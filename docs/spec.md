0. このプロダクトの一言まとめ

・サービス名（仮）：せとまち常連化AI「デジタルの店員さん」
・コンセプト：年に一度の36万人（せともの祭）を、一年中の商店街の
　　　　　　　賑わいに変える。
・対象地域：愛知県瀬戸市
・コンテスト：AWS地域創生・社会課題解決AIコンテスト
　　　　　　　選択テーマ3（地域の魅力発信・地域経済／＋人手不足の要素）
・本番発表：2026年8月4日（★残り4日）

・解く課題：
　瀬戸の高齢店主・窯元は、せともの祭で年に一度36万人と出会えるのに、
　そのつながりを継続する手段がないまま高齢化し、店を閉じていく。
　祭りの熱が「その日限り」で消えることが核心的課題。

・プロダクトの本質：
　店主側「デジタルの店員さん」と、客側「せとまちパスポート」の
　2つが対になったサービス。店主の"デジタルの手足"をAIが肩代わりし、
　祭りで生まれた出会いを一年中の関係（＝売上）に変える。

1. 全体アーキテクチャ（2つのアプリが対）
# ================================================================
■ 店主側アプリ「デジタルの店員さん」
　- 利用者：高齢の店主・窯元（代表ペルソナ：加藤さん72歳）
　- 端末：スマートフォン
　- 特徴：操作は「撮る・押す・しゃべる・確認」のみ。文字入力ゼロ。
　- 役割：出品／客への通知／問い合わせ返信／SNS投稿を、AIが自動化。

■ 客側アプリ「せとまちパスポート」
　- 利用者：祭り来場者・瀬戸ファン（代表ペルソナ：山田さん30代）
　- 端末：スマートフォン（ブラウザ、アプリインストール不要）
　- 特徴：QRを読むだけで開く。名前・住所など個人情報の入力なし。
　- 役割：出会った店の保存／コレクション化／店からの通知受信／問い合わせ。

■ 2つをつなぐ往復フロー（デモで見せる骨格）
　(1) 店主が器を出品（店主側）
　(2) 客が祭りで店を保存（客側）
　(3) 店主が新作を通知（店主側→客側）
　(4) 客が問い合わせ（客側→店主側）
　(5) 店主がAI補助で返信（店主側）
　(6) 購入・再来店（経済効果）

2. 設計原則（全機能で厳守）★最重要・変更なし

これらは「高齢店主が本当に使えるか」を担保する核であり、
プレゼンの主張の柱でもある。実装時に絶対に崩さないこと。
※4日間スプリントでも、この原則を満たす範囲でしか手を抜かない。
　（原則を壊すくらいなら、演出のままにする方を選ぶ）

【店主側の原則】
　P1. 1画面のボタンは常に1〜2個まで。情報を詰め込まない。
　P2. 文字入力は一切させない（キーボードを絶対に出さない）。
　　　入力はすべて「タップ」か「音声」で完結。
　P3. 全機能で操作を統一する。出品も返信も同じ操作手順
　　　（1タップ→話す→自動終了→確認して押す）。覚えることを増やさない。
　P4. 音声は「1回タップで録音開始、数秒の無音で自動終了」。
　　　押しっぱなし・停止ボタン操作はさせない（高齢者がつまずくため）。
　P5. AIは店主の言葉を"読みやすく整える"が、方言・口調・その人らしさ
　　　は残す。機械的な標準語化はしない。
　P6. 文字は大きく、コントラストを確保。専門用語を使わない。

【客側の原則】
　P7. アプリのインストールを要求しない（QR→ブラウザで即開く）。
　P8. 保存に個人情報入力を要求しない（ワンタップで保存完了）。
　P9. 祭りの現場で「5秒でつながりが残る」ことを最優先。

【共通の思想（プレゼンでの主張）】
　"誰も置き去りにしない設計"。店主側は文字入力ゼロ、客側はアプリ不要。

## 3-3. しゃべる画面（出品ステップ2）★サービスの肝

【表示要素】
　- 撮った器のサムネイル（大きく表示）
　- 音声認識結果の表示エリア（しゃべった言葉が文字化されて出る）
　- 波形アニメーション（録音中の視覚フィードバック）
　- 大きなマイクボタン（1つ）
　- 状態ラベル：「1回おすとはじまります」→
　　録音中「お話しください…（黙ると自動で終わります）」→「おわりました」

【動作フロー】
　1. マイクボタンを1回タップ → 録音開始（ボタンが赤くなり脈動アニメ）
　2. 店主が普段の口調で話す（例：「これは織部の小鉢でね。煮物でも、
　　 ちょっとしたおつまみでも合うよ。手にすっと馴染む大きさにしたんだ。」）
　3. 音声がリアルタイムで文字化されて画面に表示される
　4. 数秒の無音を検知 → 自動で録音停止（P4）
　5. 自動的に 3-4（AI生成中）へ

【本番の技術メモ】
　- 音声認識：Web Speech API または Amazon Transcribe 等。
　- 無音検知：一定時間（例2〜3秒）レベルが閾値以下で自動停止。
　- 認識テキストは後段の生成AIに渡す（元の口調を保持したまま）。
　- ※本改訂での位置づけ：7章 S1（今回の最優先で本物化する）

## 4-3. マイパスポート（客側ステップ2）★コレクション体験

【表示要素】
　- パスポートヘッダー：「山田さんの瀬戸めぐり」＋
　　「きょう出会ったお店：N軒」
　- スタンプグリッド（出会った店が器の絵柄つきカードで並ぶ）
　　・各カード：絵柄／店名／保存タイミング（例：たった今／10分前）
　　・最新保存店には「NEW」バッジ
　　・未取得枠は点線で「あと1軒で特典」等を表示
　- 特典バナー：「あと1軒集めると → 祭り限定エコバッグ＋加藤さんの
　　店で使える割引」
　- 補足：「集めたお店に特典が還元されます。集める＝お店を応援すること。」

【特典の設計方針】
　- 軸：お店に還元される特典（集めた店で使える割引など）。
　　→「集める＝店主を応援する」構図。企画の芯（店主が主役）と一致。
　- 添え：祭り・地域全体の特典（3軒集めると限定グッズ等）。
　　既存の紙スタンプラリー（1店千円以上でスタンプ1個、3個でエコバッグ）
　　のデジタル発展形。

【コレクション帳の意味】
　- 単なる保存リストではなく「自分だけの瀬戸焼コレクション」。
　- 祭り後も残り、店の新作通知で"生きた手帳"として更新され続ける。

　- ※本改訂での位置づけ：7章 W3（永続化は今回見送り、演出のまま）

7. 【改訂】4日間スプリントのスコープ定義

## 7-1. 基本方針
　時間が最大の制約。「全部を薄く実装」ではなく「1〜2箇所だけ本物化し、
　残りは演出のまま磨く」方が成功率が高い。
　本物化する箇所は、審査員に一番刺さる「音声→AI生成」の1点に絞る。

## 7-2. Must（必ずやる／これがないと発表できない）
　M1. v1（setomachi-mobile.html）のバグ修正・動作確認
　　　（現状ファイルに文字化け・改行コードの乱れがあったため要確認）
　M2. 発表本番で使う実機（機種・OS・ブラウザ）でのリハーサル確認
　M3. 往復フロー（出品→通知→問い合わせ→返信）が「途切れず」
　　　通しで動くこと（演出のままでも良いので、流れが破綻しないこと）
　M4. デプロイ済みのURLでアクセスできる状態（審査要件：クラウド上で
　　　動作していることのデモが必須）

## 7-3. Should（時間が許せばやる／本物化で説得力が跳ねる部分）
　S1. 店主側 3-3（しゃべる）：Web Speech API による実際の音声認識
　　　※ブラウザ標準機能。バックエンド不要でその場で実装可能。
　　　※本番使用端末がSafari（iPhone）の場合は動作が不安定なため、
　　　　実機確認必須。不安なら演出のままにする判断もあり。
　S2. 店主側 3-4〜3-5（AI生成）：認識テキストを実際にLLM（Google Gemini API）
　　　に渡し、本物の紹介文・通知文を生成
　　　※方言・口調を保持するプロンプト設計が肝（P5）
　　　※簡易なサーバーレス関数（Lambda 1本など）でAPIキーを保護する
　　　　最小構成で十分。Cognito・本格DB構築は今回は不要と判断。

## 7-4. Won't（今回はやらない／演出のまま発表する）
　W1. 実際の端末カメラ撮影（getUserMedia）→ 現行の演出のままでよい
　W2. 実際のQRコード生成・読み取り → 現行の演出のままでよい
　W3. 会員データ・パスポート・フォロー関係の永続化（本格DB）
　　　→ 発表用は演出のまま、または簡易なローカル状態管理で代替
　W4. AI返信ドラフト（3-8〜3-9）の本物化 → 演出のまま
　W5. SNS投稿の実生成、写真のAI調整、特典集計ロジックの作り込み
　　　→ 完全に見送り

## 7-5. 4日間の作業割り当て（案）
　Day1（7/31）：v1の文字化け・動作確認、本番端末でのブラウザ確認、
　　　　　　　　S1（音声認識）の実装着手
　Day2（8/1） ：S1完成、S2（AI生成をLambda経由で本物化）着手
　Day3（8/2） ：S2完成、デプロイ（Amplify等）、通し動作確認
　Day4（8/3） ：リハーサル、バグ修正のみ（新機能の追加は禁止）
　8/4：本番発表

## 7-6. フォールバック方針（重要）
　S1・S2が間に合わない場合、無理に本番投入せず、v1の演出のまま
　発表する。審査要件（6章）を満たしているため、演出のままでも
　「コンセプトデモ」として正式に評価対象になる。
　→ 深追いして往復フロー全体が壊れるリスクの方が、
　　演出のまま発表するリスクより大きい。

## 7-7. 追加スコープ（コード動作確認後に追加決定）

　S1・S2のローカル動作確認が完了したため、外部アカウント・外部リンクを
　必要としない範囲で、以下を追加実装する。W3・W4の一部はこの決定により
　Won'tから外れる。

　A1. ✅実装済み 価格表示（3-5画面）をタップで切り替え可能にする
　　　あらかじめ用意した2〜3種の価格帯をタップごとに切り替える。
　　　数字キーボードは表示しない（P6維持）。外部通信なし。
　A2. ✅実装済み 返信フロー（3-8〜3-9）もS1・S2と同じ音声入力+Gemini生成にする
　　　既存のLambda・Gemini連携をそのまま流用。W4は撤回し、実装対象とする。
　A3. ✅実装済み 客側パスポート（4-2〜4-3）の保存をlocalStorageで永続化する
　　　サーバー・DBは使わず、ブラウザ内のlocalStorageのみで完結させる。
　　　W3の「DB構築は見送り」は維持しつつ、DBを使わない範囲で実現する。
　A4. タイトル/イントロ画面を追加する
　　　リンクを開いた直後、いきなり店主側ホーム画面が表示され、
　　　初見の審査員がプロダクトの概要を理解できない問題を解消する。
　　　サービス名・一言コンセプト・簡単な使い方ガイドを表示する
　　　オーバーレイ画面を追加し、「はじめる」ボタンで既存の店主側
　　　ホーム画面（4-1）に進む。既存画面のロジック・原則（P1〜P9）
　　　には影響しない、独立した追加画面とする。外部通信なし。
　　　完成したサービスとして見せるため、「プロトタイプ」「デモ」
　　　等、未完成を想起させる語は使わない。

　対象外のまま（変更なし）：
　　W1（カメラ実装）、W2（QR実装）、W5（SNS投稿の実生成・写真AI調整・
　　特典集計ロジック）は、引き続き演出のままとする。

## 8-1. 全体構成（簡易図）

```
[スマホのブラウザ]
   ├─ フロントエンド（HTML/CSS/JS・setomachi-mobile.html）
   │     ├─ Web Speech API（音声認識）
   │     └─ fetch() でバックエンドを呼び出す
   ↓ HTTPS
[Lambda Function URL]
   ↓
[Lambda関数]
   ├─ 音声認識テキストを受け取る
   ├─ Google Gemini API を呼び出す
   └─ 生成結果（タイトル・紹介文・通知文）をJSONで返す
   ↓
[フロントエンドが結果を画面に反映]

[AWS Amplify]（フロントエンドのホスティング・GitHub連携で自動デプロイ）
```

　- HTML / CSS / JavaScript（Vanilla）

　- Lambda Function URL

## 8-4. AI生成
　- Google Gemini API（Gemini 3.5 Flash、無料枠。2026年8月時点でgemini-2.5-flash
　　は新規アカウントで404となったため、gemini-3.5-flashに変更）

## 8-5. デプロイ・ホスティング
　- AWS Amplify（フロントエンド）
　- AWS Lambda（バックエンド）

## 8-6. リポジトリ・バージョン管理
　- GitHub

## 8-7. データ保存・認証
　- データ保存：なし（ブラウザの一時的な状態のみ）
　- 認証：なし
