0. このプロダクトの一言まとめ

・サービス名（仮）：せとまち常連化AI「デジタルの店員さん」
・コンセプト：年に一度の36万人（せともの祭）を、一年中の商店街の
　　　　　　　賑わいに変える。
・対象地域：愛知県瀬戸市
・コンテスト：AWS地域創生・社会課題解決AIコンテスト
　　　　　　　選択テーマ3（地域の魅力発信・地域経済／＋人手不足の要素）
・本番発表：2026年8月4日

・解く課題：
　瀬戸の高齢店主・窯元は、せともの祭で年に一度36万人と出会えるのに、
　そのつながりを継続する手段がないまま高齢化し、店を閉じていく。
　祭りの熱が「その日限り」で消えることが核心的課題。

・プロダクトの本質：
　店主側「デジタルの店員さん」と、客側「せとまちパスポート」の
　2つが対になったサービス。店主の"デジタルの手足"をAIが肩代わりし、
　祭りで生まれた出会いを一年中の関係（＝売上）に変える。

1. 全体アーキテクチャ（2つのアプリが対）
================================================================
■ 店主側アプリ「デジタルの店員さん」　- 利用者：高齢の店主・窯元（代表ペルソナ：加藤さん72歳）　- 端末：スマートフォン　- 特徴：操作は「撮る・押す・しゃべる・確認」のみ。文字入力ゼロ。　- 役割：出品／客への通知／問い合わせ返信／SNS投稿を、AIが自動化。

■ 客側アプリ「せとまちパスポート」
　- 利用者：祭り来場者・瀬戸ファン（代表ペルソナ：山田さん30代）
　- 端末：スマートフォン（ブラウザ、アプリインストール不要）
　- 特徴：QRを読むだけで開く。名前・住所など個人情報の入力なし。
　- 役割：出会った店の保存／コレクション化／店からの通知受信／問い合わせ。

■ 2つをつなぐ往復フロー（デモで見せる骨格）
　(1) 店主が器を出品（店主側）
　(2) 客が祭りで店を保存（客側）
　(3) 店主が新作を通知（店主側→客側）
　(4) 客が問い合わせ（客側→店主側）
　(5) 店主がAI補助で返信（店主側）
　(6) 購入・再来店（経済効果）

2. 設計原則（全機能で厳守）★最重要

これらは「高齢店主が本当に使えるか」を担保する核であり、
プレゼンの主張の柱でもある。実装時に絶対に崩さないこと。

【店主側の原則】
　P1. 1画面のボタンは常に1〜2個まで。情報を詰め込まない。
　P2. 文字入力は一切させない（キーボードを絶対に出さない）。
　　　入力はすべて「タップ」か「音声」で完結。
　P3. 全機能で操作を統一する。出品も返信も同じ操作手順
　　　（1タップ→話す→自動終了→確認して押す）。覚えることを増やさない。
　P4. 音声は「1回タップで録音開始、数秒の無音で自動終了」。
　　　押しっぱなし・停止ボタン操作はさせない（高齢者がつまずくため）。
　P5. AIは店主の言葉を"読みやすく整える"が、方言・口調・その人らしさ
　　　は残す。機械的な標準語化はしない。
　　　（例：「〜だよ」「〜でね」「ありがとねぇ」等をそのまま活かす）
　P6. 文字は大きく、コントラストを確保。専門用語を使わない
　　　（「出品」→「あたらしい器をだす」等、やさしい言葉に）。

【客側の原則】
　P7. アプリのインストールを要求しない（QR→ブラウザで即開く）。
　P8. 保存に個人情報入力を要求しない（ワンタップで保存完了）。
　P9. 祭りの現場で「5秒でつながりが残る」ことを最優先。

【共通の思想（プレゼンでの主張）】
　"誰も置き去りにしない設計"。店主側は文字入力ゼロ、客側はアプリ不要。
　デジタルが苦手な人・急いでいる人の両方を取りこぼさない。

3. 店主側アプリ 詳細仕様

---

## 3-1. ホーム画面

【表示要素】
　- ヘッダー：「デジタルの店員さん」＋店名（例：加藤さんのお店）
　- 大きな主要ボタン1つ：「📷 あたらしい器をだす」
　- 通知カード：「お客さんからメッセージ」＋未読件数バッジ＋
　　メッセージ冒頭のプレビュー（例：「織部の小鉢、まだ買えますか？」）
　- 補助テキスト：「やることは、撮って ひとこと 話すだけ。
　　文字は打たなくてだいじょうぶです。」

【遷移】
　- 「あたらしい器をだす」→ 3-2（カメラ）
　- 通知カード → 3-6（返信フロー：受信）

---

## 3-2. 写真をとる画面（出品ステップ1）

【表示要素】
　- カメラプレビュー領域（本番は端末カメラを起動）
　- 中央にフレームガイド枠＋補助「器をまんなかにいれてください」
　- 丸いシャッターボタン
　- 戻る矢印（前画面へ）

【動作】
　- シャッター押下 → 撮影 → 3-3（しゃべる）へ
　- 本番仕様：撮影後に「とりなおす／これでいい」の確認を挟む
　　（プロトタイプでは簡略化）

【本番の技術メモ】
　- 端末カメラAPI（getUserMedia / input capture）で撮影。
　- 撮影画像は後段のAI画像調整・商品ページ生成に渡す。

---

## 3-3. しゃべる画面（出品ステップ2）★サービスの肝

【表示要素】
　- 撮った器のサムネイル（大きく表示）
　- 音声認識結果の表示エリア（しゃべった言葉が文字化されて出る）
　- 波形アニメーション（録音中の視覚フィードバック）
　- 大きなマイクボタン（1つ）
　- 状態ラベル：「1回おすとはじまります」→
　　録音中「お話しください…（黙ると自動で終わります）」→「おわりました」

【動作フロー】
　1. マイクボタンを1回タップ → 録音開始（ボタンが赤くなり脈動アニメ）
　2. 店主が普段の口調で話す（例：「これは織部の小鉢でね。煮物でも、
　　 ちょっとしたおつまみでも合うよ。手にすっと馴染む大きさにしたんだ。」）
　3. 音声がリアルタイムで文字化されて画面に表示される
　4. 数秒の無音を検知 → 自動で録音停止（P4）
　5. 自動的に 3-4（AI生成中）へ

【本番の技術メモ】
　- 音声認識：Web Speech API または Amazon Transcribe 等。
　- 無音検知：一定時間（例2〜3秒）レベルが閾値以下で自動停止。
　- 認識テキストは後段の生成AIに渡す（元の口調を保持したまま）。

---

## 3-4. AI生成中画面（出品ステップ3）

【表示要素】
　- ローディングスピナー
　- 「加藤さんのことばから お店のページをつくっています」
　- 進捗ステップ表示（順に切り替わる）：
　　 「写真をととのえています…」
　　→「ことばから紹介文をつくっています…」
　　→「お知らせ文とSNS投稿をつくっています…」

【動作】
　- 生成完了後、自動的に 3-5（生成結果）へ

【本番の技術メモ】
　- 生成AI（LLM）に「音声認識テキスト＋画像」を渡し、以下を一括生成：
　　・商品タイトル　・紹介文　・使い方の提案タグ　・（価格候補）
　　・客への通知文　・SNS投稿文（Instagram/TikTok/X用）
　- プロンプトには「店主の口調・方言を保持」の指示を必ず入れる（P5）。

---

## 3-5. AI生成結果画面（出品ステップ4）★見せ場

【表示要素：自動生成された商品ページのプレビュー】
　- 器の写真（AI調整済み）＋「AIが作成」バッジ
　- カテゴリタグ（例：織部／小鉢／普段づかい）
　- タイトル（例：「織部の小鉢 ― 普段づかいにちょうどいい一枚」）
　- 紹介文（店主の言葉を活かした2〜3文）
　- 価格表示（「タップで変更」＝価格だけは選択式のUI。数値入力させない）
　- 補足ノート：「加藤さんが話した『手にすっと馴染む』をそのまま
　　活かしています。方言や言い回しは残したまま整えました。」
　- SNS投稿の自動生成表示（Instagram / TikTok / X の3チップ）

【操作ボタン（2つ）】
　- 「もういちど話す」→ 3-3へ戻る（AIが作り直す）
　- 「これでだす」→ 3-6（完了）へ

【重要仕様】
　- 店主は文章を打ち直さない。気に入らなければ「もういちど話す」で
　　再度しゃべる→AIが作り直す、というループのみ。
　- 価格は「よく使う価格帯をタップ」など選択式（数字キーボードを出さない）。

　　　　いつでも寄ってちょうだい。待っとるでね。」
　- 補足：「加藤さんの口調（〜だよ・〜でね）はそのまま。きれいに
　　しすぎず、加藤さんのことばで届けます。」

【操作ボタン（2つ）】
　- 「もういちど話す」→ 3-8へ
　- 「これで送る」→ 3-10（送信完了）へ

【重要仕様（P5の具体化）】

## 4-1. 祭り会場・店先（客側ステップ0）

【シチュエーション】
　祭り会場で、客が加藤さんの店の器を気に入る。店先にQRの木札。
【表示要素（デモ演出）】
　- 店の看板表示（例：加藤陶器店 ― 織部 ぐい呑・小鉢）
　- QRコード
　- 補助：「この器、気に入った。QRを読むとお店を持ち帰れる」
　- 「📷 QRコードを読む」ボタン（デモ用。実際は端末のカメラで読む）
【遷移】QR読み取り → 4-2へ

【入口の設置場所（本番の展開）】
　- 各店の店先（木札QR）
　- パルティせと、尾張瀬戸駅など、36万人が必ず通る導線
　- Instagram / TikTok / X（遠方の若者向けの入口）

---

## 4-2. 店ページが開く（客側ステップ1）★アプリ不要

【表示要素】
　- ヘッダー：「せとまちパスポート」＋「アプリ不要・ブラウザで開く」
　- 店カード：カバー画像、店主アバター、店名、商店街名
　- 店主の一言（音声から生成された紹介の引用）
　　例：「これは織部の小鉢でね。手にすっと馴染む大きさにしたんだ。」
　- 大きなボタン「＋ このお店をパスポートに保存」
　- 補足：「名前も住所も入れません。ポンと押すだけ。」
【遷移】保存ボタン → 4-3へ

【重要仕様】
　- QRを読むとブラウザで即表示（P7）。ネイティブアプリ導線にしない。
　- 保存に会員登録・個人情報入力を挟まない（P8）。
　- 本番：将来「ホーム画面に追加（PWA）」で通知強化できる余地を残す。

---

## 4-3. マイパスポート（客側ステップ2）★コレクション体験

【表示要素】
　- パスポートヘッダー：「山田さんの瀬戸めぐり」＋
　　「きょう出会ったお店：N軒」
　- スタンプグリッド（出会った店が器の絵柄つきカードで並ぶ）
　　・各カード：絵柄／店名／保存タイミング（例：たった今／10分前）
　　・最新保存店には「NEW」バッジ
　　・未取得枠は点線で「あと1軒で特典」等を表示
　- 特典バナー：「あと1軒集めると → 祭り限定エコバッグ＋加藤さんの
　　店で使える割引」
　- 補足：「集めたお店に特典が還元されます。集める＝お店を応援すること。」

【特典の設計方針】
　- 軸：お店に還元される特典（集めた店で使える割引など）。
　　→「集める＝店主を応援する」構図。企画の芯（店主が主役）と一致。
　- 添え：祭り・地域全体の特典（3軒集めると限定グッズ等）。
　　既存の紙スタンプラリー（1店千円以上でスタンプ1個、3個でエコバッグ）
　　のデジタル発展形。

【コレクション帳の意味】
　- 単なる保存リストではなく「自分だけの瀬戸焼コレクション」。
　- 祭り後も残り、店の新作通知で"生きた手帳"として更新され続ける。

---

## 4-4. 新作お知らせ（客側ステップ3・祭りの数日後）

【シチュエーション】
　祭りが終わって数日後、保存した店（加藤さん）が新作を出品。
　その通知がパスポートに届く（＝店主側3-6と連動）。
【表示要素】
　- 通知カード：店名＋「新作」＋経過時間（例：3日後）
　- 新作画像
　- 店主の一言（音声から生成）
　　例：「新しいぐい呑が焼き上がったよ。晩酌のおともにどうぞ。」
　- ボタン2つ：「気になる」「問い合わせる」
　- 補足：「祭りが終わってもつながりは続く。コレクション帳が
　　"生きた手帳"に育つ。」
【遷移】「問い合わせる」→ 4-5へ

---

## 4-5. 問い合わせ送信（客側ステップ4）→ 経済効果へ

【表示要素】
　- 客が送った問い合わせを吹き出しで表示
　　（例：「先日の織部の小鉢、まだ購入できますか？2つ欲しいのですが。」）
　- 送信完了表示：「加藤さんに届きました」「お店側で『デジタルの
　　店員さん』が返信をお手伝いします。」
【連動】
　- この問い合わせが店主側3-7（受信）に届き、往復が一周する。
　- その後：取り置き・再来店・購入（＝祭りの2日間が一年中の売上に変わる）。

6. プロトタイプ v1 の実装状況と本番との差分

【v1で実装済み（HTML/CSS/JS 1枚、setomachi-mobile.html）】
　- 店主側／客側をタブで切り替え
　- 全画面遷移（出品5画面・返信4画面・客側5画面）
　- 音声入力の演出（タップ→文字が順に表示→自動停止のアニメ）
　- AI生成の演出（スピナー＋ステップ表示）
　- スマホ最適化（1台表示・タップ操作の確実化）

【v1では"演出"であり、本番で実装が必要なもの】
　- 実際の端末カメラ撮影
　- 実際の音声認識（Web Speech API / Amazon Transcribe等）
　- 実際の生成AI（商品ページ・通知文・返信ドラフト・SNS投稿）
　　※店主の口調保持のプロンプト設計が肝
